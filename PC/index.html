Why another notebook?

Jupyter notebooks are great for exploring, but the notebook you see is not always the program that runs

  • Cells can be run in any order
  • Deleting a cell doesn’t delete its variables
  • Widgets only update the cell they live in
  • .ipynb is JSON with outputs inside, so git diffs are noisy

In a study of ~1.4 million GitHub notebooks, only 24% ran without errors and only 4% reproduced their saved results

Pimentel et al., MSR 2019

marimo’s answer: make the notebook a reactive program. Each cell declares what it reads and defines, and marimo keeps every output consistent with the code

How marimo runs a notebook

marimo reads each cell’s code to find the names it defines and the names it reads. That gives a dependency graph (a DAG)

  • Change a cell → marimo reruns everything that depends on it, and nothing else
  • Each global name is defined in one cell
  • Delete a cell → its variables are deleted too
  • _name variables stay private to their cell
  • UI elements (mo.ui.*) are just variables, so interacting with one reruns the cells that read .value

Move the slider (orange) and only the blue cells rerun

## [WHERE]{.kw .where} filters rows

```{python .marimo}
yob = mo.ui.range_slider(1935, 2005, value=[1950, 1975], label="Year of birth")
yob
```

```{sql .marimo}
#| engine: con
SELECT person_id FROM person LIMIT 6
```

Markdown plus code blocks. Quarto controls the layout; the marimo engine makes the blocks reactive

@app.cell
def _(mo):
    yob = mo.ui.range_slider(1935, 2005, value=[1950, 1975], label="Year of birth")
    yob
    return (yob,)


@app.cell
def _(con, mo, yob):
    where_df = mo.sql(f"""
        SELECT person_id FROM person
        WHERE year_of_birth BETWEEN {yob.value[0]} AND {yob.value[1]}
    """, engine=con)
    return (where_df,)

Plain Python. Function arguments are the cell’s inputs, and return values are its outputs. Git-friendly, importable, and it runs with python file.py

How the interactivity works

  • @interact builds the widgets and reruns one function
  • Linked widgets need .observe() callbacks and an Output widget
  • Chart selections go through alt.JupyterChart + anywidget
  • The notebook includes a hidden state exercise

)

Render it

How it works

  • engine: marimo runs each ```{python .marimo} block as a marimo cell
  • The page is static HTML with islands: interactive widgets that run in the browser through Pyodide (Python compiled to WebAssembly)
  • Quarto owns the layout: columns, slides, themes, SCSS, chalkboard
  • Viewers can’t edit the code

Sharing with molab

molab is marimo’s hosted notebook service: like Colab, but for marimo notebooks

  • Point it at a notebook on GitHub
  • Static preview loads instantly; Run starts a server
  • Add /wasm to run it in the viewer’s browser, with no login or server
  • Packages install when they’re imported

Which one, when?

Jupyter

  • You’re exploring on your own
  • You need a Jupyter-only extension or kernel (R, Julia)
  • Your team or platform already runs on .ipynb

Quarto

  • You’re presenting or publishing
  • You need full control of the layout and theme
  • Readers should see results, not edit code

marimo

  • Students should run and change the analysis
  • You want reproducible, git-friendly notebooks
  • The notebook should also work as an app or a script

For this course: teach from the Quarto deck, and practise in the marimo notebook. The Jupyter version shows what reactivity saves you
